Resolved since first pass

5 items

The original assessment listed five blockers. One turned out to be a wrong assumption about how this app's access control works; the other four are now fixed and covered by real HTTP round-trip tests, not mocks. One related item was investigated and deliberately left as-is — see its note below.

Corrected

Permission assignment was never actually a code gap

This app has no Role-based ACL — permissions live directly on User.permissions, assigned via the existing Staff Create/Edit screen. The Clinical permission set was already there and already assignable with zero further code. No fix needed; this is an operational step for whoever runs the pilot.

app/Traits/AccessTrait.php — $clinicalModule · UserController
Fixed

Role-gated steps now check a real permission

This app has no reliable "job role" field to check against (Title/Qualification are free-text). Added two capacity permissions — Act As Ward Nurse, Act As Consultant — checked before a role-gated process step or a doctor/nurse patient claim goes through. Unrecognized required_role values fail closed.

ClinicalProcessPanel::assertRoleGateSatisfied() · CaptureObservations::claim()
Fixed

Imaging now has a real endpoint at the dispatched path

Added POST /api/v1/imaging/facts/{factType} behind the existing VerifyImagingApiKey middleware, delegating to the same ImagingOrderReceiver the local driver already used. Also corrected the auth header the dispatcher sends for Imaging specifically (X-Imaging-API-Key, not a generic Bearer token) to match that middleware exactly. Flipping DISPATCH_DRIVER=http for Imaging now works end to end.

Fixed

LIMS has a real, HMAC-verified inbound webhook

Added POST /api/v1/clinical/lab-proxy/{eventType}, signature-verified against the raw request body before anything reaches LimsIntegrationProxyService — fails closed on a missing, wrong, or tampered signature. A genuinely external LIMS now has somewhere real to call.

Investigated, left as-is

branch_id scoping is a repo-wide pattern, not a Clinical bug

Confirmed Imaging and Inventory scope by business_id only too — branch_id is stored but never filtered anywhere in this codebase. Needs attention

7 items

Real gaps worth planning for — none of these block a careful pilot, but all of them will surface under real usage.

Testing

Nothing has been clicked through in a browser

All 205 tests are PHPUnit and Livewire-component level (two of them now real HTTP round-trips, which is new — see Resolved above). The run-kashtre skill was never invoked this session — no one has actually seen the ward board, the chart page, or the MAR render in an actual browser window.

Performance

Everything runs inline, synchronously

QUEUE_CONNECTION=sync means FHIR export, external-referral PDF generation, and every consumption/dispatch call block the HTTP request that triggered them. Fine at pilot scale; worth queuing before real ward load.

Concurrency

Race conditions are untested

Two nurses completing the same process step, or administering the same MAR dose, at the same moment — none of this was exercised. The step/dose tables have unique constraints that will catch some of it, but the user-facing failure mode hasn't been designed.

UI

Interfaces are functional, not refined

Drug and lab-test entry is plain text match, not autocomplete. No list in the module paginates. Error and loading states are Livewire's defaults. This was scoped as working software, not a finished product.

Infra

Local MySQL is fragile under concurrent migrations

Mid-build, several overlapping migrate:fresh runs corrupted the isolated test database's InnoDB dictionary. Recoverable by recreating the database, but worth a line in onboarding docs so a teammate doesn't lose an afternoon to it.

Content

Clinical reference data is illustrative, not exhaustive

The drug-interaction dictionary, ICD-11 codes, and lab test catalog all ship with a handful of representative rows to prove the mechanics work — not real facility content. Someone with clinical authority needs to own populating these before go-live.

Finance

Entitlements and postpaid billing are recorded, not acted on

Package entitlements have consumption logic but no allocation UI — Main Module needs to create the rows. Postpaid billing events are durable facts with no consumer yet; nothing turns them into an actual invoice.

Deferred by design

7 items

Scoped out on purpose during the build, each with a reason left in the code. Listed here so none of them are a surprise later.

Ch. 8

Real-time voice dictation

Text-based AI extraction only — streaming speech-to-text needs mic capture and a persistent WebSocket, a materially bigger build.

Ch. 6

Full eGFR (CKD-EPI) calculation

The renal-safety check reads an eGFR value already on the chart rather than computing it from creatinine, age, and sex.

Ch. 9

Order Automation Engine & Order Sets

Daily ward-round auto-orders and pathway bundles — not started. Needs its own scheduling and configuration design.

Ch. 4

Demand-ledger intent & ward tote handshake

Two Inventory ICD flows (pre-availability demand logging, the 5-digit tote release token) sit outside what "consumption decrements stock" needed.

Ch. 3 / 7

Cancel-order flows

The contract methods exist for both Imaging and LIMS; no UI or dispatch wiring calls them yet.

Ch. 5

Transfer's bed swap

Admission and discharge move a bed automatically; transfer's steps exist but don't yet release the old bed and allocate the new one.

Ch. 9

IPS / C-CDA export

FHIR R4 JSON only — IPS is a profile on the same resources, not a separate mapping worth building speculatively.

Suggested rollout sequence

  1. Assign permissions to your pilot ward's staff

    Check the Clinical boxes on the Staff Edit screen for the nurses, doctors, and consultants on one ward — including their Act As Ward Nurse / Act As Consultant capacity, now that those gate role-specific steps. No code work involved.

  2. Run one ward through the full loop

    Admission → chart → orders → discharge, watched end to end, before adding a second ward.

  3. Populate real reference data

    Hand the DDI dictionary, reason codes, and item metadata to whoever owns clinical content at the facility — the mechanics are proven, the content isn't real yet.

  4. Move off synchronous execution, add browser smoke tests

    Queue the heavy operations and get eyes on the actual rendered UI before scaling past pilot load.

  5. Decide on branch-level isolation, deliberately

    A repo-wide call, not a Clinical one — worth making once, on purpose, across Imaging/Inventory/Clinical together, rather than each module drifting its own way.

  6. Revisit LIMS and the AI Gateway last

    Both are fully stubbed, gracefully degrade today, and now have real HTTP endpoints proven end to end. Nothing else in this module depends on either becoming real.
